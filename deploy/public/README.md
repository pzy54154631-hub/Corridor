# Corridor 公开模式部署

这个目录里是把网页演示部署成公开 HTTPS 站点所需的全部文件，不含任何秘密。

目标机：腾讯云轻量香港，4 核 8G，Ubuntu 22.04，x86_64。公开域名 `43-154-247-126.sslip.io`。

网页进程只监听 `127.0.0.1:8772`，以非 root 用户 `corridor` 运行。Caddy 负责 TLS 和 80、443 端口。防火墙只开 22、80、443。

## 脚本规划模式：不需要模型密钥

默认部署只用脚本规划，不调用模型，也不产生费用。**下面“打开真模型”一节的三件事在这个模式下都不需要做**，站点照样能上线。

上线步骤：

1. 在发布机上打包公开导出树，并算出摘要：

   ```
   tar czf corridor-public.tar.gz -C <导出目录> .
   sha256sum corridor-public.tar.gz
   ```

2. 把归档和 `deploy/public/install.sh` 传到服务器。其余部署文件都在归档里，校验通过后才使用。

3. 在服务器上运行，摘要用发布机上算出的值，不要在服务器上重新算：

   ```
   sudo bash install.sh --archive corridor-public.tar.gz --sha256 <摘要>
   ```

   可以在任何目录运行，`--archive` 可以写相对路径：脚本先把它解析成绝对路径，再切到 `/` 继续。

4. 腾讯云控制台的实例防火墙也只放行 TCP 22、80、443。

5. 按“验收”一节逐项确认，全部通过之后才开放公网：

   ```
   sudo bash /opt/corridor/current/deploy/public/open_public.sh
   ```

`install.sh` 不对公网开放。它结束时门禁仍然关闭，外部访问得 503。

脚本做的事，按顺序：

1. 校验归档 sha256，通过之后才解压。
2. 安装固定版本的 Caddy 2.11.7 和 uv 0.13.1，两者都校验摘要。
3. 配置 ufw，只放行 22、80、443。
4. 用 uv 安装 Python 3.11 和 `uv.lock` 锁定的依赖，放进 `/opt/corridor/releases/<编号>/`。编号是归档 sha256 的前 12 位。服务账号只在构建期间能写这些目录；构建结束后 `releases`、`python` 和 uv 缓存全部归 root，并用服务账号实测确实写不了，否则失败。
5. 检查这个 release 具备公开模式能力。
6. 校验 Caddyfile，停掉旧服务，关上门禁：`corridor-gate.caddy` 让所有非回环来源得 503，只有证书申请不受影响。
7. 等证书签发，再从本机的非回环地址实测门禁确实得 503。门禁不生效就不启动新版本。
8. 切换符号链接 `/opt/corridor/current`，启动服务，检查公开模式确实生效。
9. 走回环地址核对 HTTPS、HTTP 跳转和 `Server` 头。
10. 用金丝雀实测手机配对路径不进入 Caddy 和进程的 journal。

台账与 journal 在 `/var/lib/corridor`，环境文件在 `/etc/corridor/web-public.env`（0600，属主 root）。它们都在 release 之外，升级和回滚都不动。重新运行安装脚本不会覆盖已有的环境文件，但会重新关上门禁，所以升级之后同样要验收并运行 `open_public.sh`。

## 打开真模型：用户要做的三件事

这三件事只有用户本人做。部署代理不读取、不复制密钥和口令。

**第一件：放 `.env.deepseek`。** 文件只写一行 `LLM_API_KEY=<DeepSeek 密钥>`：

```
sudo install -m 0640 -o root -g corridor /dev/null /etc/corridor/live/.env.deepseek
sudo nano /etc/corridor/live/.env.deepseek
```

服务器上只放这一个凭据文件。

**第二件：运行 access_setup。** 下面这条命令会运行 `python -m corridor.web.access_setup`，把它打印的验证子写进环境文件，打开开关，再重启服务：

```
sudo bash /opt/corridor/current/deploy/public/enable_live.sh
```

**第三件：保存口令。** 口令由工具随机生成，只在终端显示一次，不进任何文件。把它保存好，只通过提交表单的备注交给评委。不要写进仓库、文档或聊天记录。

口令会进入终端回显：终端的滚动缓冲、`script` 或 sudo 的会话录制、屏幕录制、自动化工具的日志都可能留下它。不要在这些环境里运行 `enable_live.sh`，也不要把它的输出重定向到文件。运行之后清空终端。

再次运行 `enable_live.sh` 会换一个新口令，旧口令随即失效。

要验收口令解锁，就在开放公网之前运行 `enable_live.sh`。

关闭真模型：把 `/etc/corridor/web-public.env` 里的 `CORRIDOR_LIVE=1` 改成 `CORRIDOR_LIVE=0`，再运行 `sudo systemctl restart corridor-web`。脚本规划照常工作。

## 回滚

```
sudo bash /opt/corridor/current/deploy/public/rollback.sh          # 列出已安装的 release
sudo bash /opt/corridor/current/deploy/public/rollback.sh <编号>
```

- 只能回滚到具备公开模式能力的 release。目标不合格时脚本拒绝执行，服务保持原样。
- 旧 release 的回滚脚本切不回新版。能力检查用的是脚本所在 release 里的 `capability.py`，新版的数值超过旧版的上界就会被拒绝，例如在途上限从 6 调到 12 之后。回滚之后 `/opt/corridor/current` 指向旧版，上面两条命令运行的正是旧脚本，所以切回新版要用新 release 自己的脚本：

  ```
  sudo bash /opt/corridor/releases/<新编号>/deploy/public/rollback.sh <新编号>
  ```

- 回滚也带回旧版的限额。下面“如实说明”里的额度说的是当前版本，回滚之后以目标 release 的代码为准。
- 切换之后如果启动失败，服务保持下线，不会再自动换版本。
- 回滚不动台账，已花费的预算不会重置。
- 更新和回滚都会重启进程，所有会话随之丢失。

## 失败时的行为

下面说的“下线”都是 `systemctl disable --now corridor-web`：服务停止，机器重启也不会自己回来。Caddy 对外返回 502。

- sha256 不符：不解压。已在运行的服务也随之下线，重新运行安装脚本才会恢复。
- `install.sh` 通过参数检查之后的任何其他失败：下线，不回退到更弱的版本。
- 门禁实测不是 503：不启动新版本，下线。
- `enable_live.sh` 重启失败或重启后没有通过检查：下线。这时环境文件已经是 `CORRIDOR_LIVE=1`，处理之后重新运行它，会换一个新口令。
- `open_public.sh` 的任何失败：下线。重新运行安装脚本，门禁会重新关上。
- 证书签发失败：服务保持下线，不用自签证书，也不开明文站点。先看 `journalctl -u caddy`。处理之后重新运行安装脚本。
- `CORRIDOR_LIVE=1` 但验证子缺失或格式不对：进程拒绝启动。
- 防火墙里有其他放行规则：安装脚本报错退出，由操作者先删除。
- 进程崩溃或被内存上限杀掉：`Restart=always` 在 3 秒后拉起。没有健康检查自动重启。

## 验收

本地无法验证下面这些内容，部署后必须在目标机上逐项确认。

**任何一项不通过，就让站点下线，不带问题开放或继续开放：**

```
sudo systemctl disable --now corridor-web
```

门禁关闭时，验收者的浏览器走 SSH 隧道，这样 Caddy 看到的对端是回环地址，证书、Host 和 Origin 都和公开访问时一样：

```
ssh -L 8443:127.0.0.1:443 <服务器>
msedge --host-resolver-rules="MAP 43-154-247-126.sslip.io:443 127.0.0.1:8443" https://43-154-247-126.sslip.io/
```

开放之前逐项确认：

- `caddy validate` 通过。本地没有运行过 Caddy，Caddyfile 的语法只对照了 v2.11.7 的源码和文档。安装脚本会先校验。
- `journald` 中没有手机配对路径。安装脚本用金丝雀实测，失败即下线。还要在目标机上补测超时和畸形请求。
- 从外部访问公开网址：DNS 和证书链有效，HTTP 跳转 HTTPS，业务页面得 503。
- 经隧道核对 Host 与 Origin、重启和回滚。
- 经隧道用 Playwright 加系统 Edge 跑一次真实浏览器旅程，覆盖首屏横幅、Cookie 属性和口令解锁。
- 请求体、头与体读取超时的实际效果，以及每会话内存占用。
- 限流补充速率和在途上限，按真机吞吐复核。

运行 `open_public.sh` 之后，从外部不经隧道再跑一次同样的浏览器旅程。不通过同样下线。

下线之后要重新运行安装脚本，它会重新关上门禁并重新启用服务。

## 台账与核账

- 台账只有一个位置：`/var/lib/corridor/journal/live-ledger.sqlite3`。公开模式下这个路径写死在代码里，`LIVE_JOURNAL_DIR` 改成别的值，进程拒绝启动。
- 台账只由 `enable_live.sh` 第一次运行时创建，同时写下持久标记 `/etc/corridor/ledger-initialized`。网页进程从不创建台账。
- 台账丢失或损坏时，真模型立即关闭，站点继续按脚本规划工作。`enable_live.sh` 也拒绝继续。

恢复之前必须人工核账：

1. 到 DeepSeek 控制台查实到目前为止的累计花费。
2. 有完好的备份，就把它放回原位，属主 `corridor`，权限 0600，核对它记录的花费不低于账单。这就完成了，不需要第 3、4 步。
3. 把损坏的文件移走，不要删除。
4. 按核出的金额重建台账，累计预算从这个数接着算：

   ```
   sudo runuser -u corridor -- /opt/corridor/current/.venv/bin/python -m corridor.web.ledger_setup --journal-dir /var/lib/corridor/journal --spent-cny <核出的元数>
   ```

这一步不换口令，也不需要重启服务。工具不会覆盖已有的文件。

评审结束后删除 journal 也会删除预算历史，此后 `/etc/corridor/ledger-initialized` 仍在，真模型保持关闭。整台机器重建时标记也没了，这时累计预算只能靠上面的人工核账接续：`enable_live.sh` 无从知道历史花费，运行它之前要先用 `ledger_setup` 写入核出的金额。

## 如实说明

- `sslip.io` 是第三方服务。需要 DNS 可控时，可以另买一个独立域名。换域名要改发布树里 Caddyfile 的站点名并重新打包，同时改服务器环境文件的 `CORRIDOR_WEB_PUBLIC_HOST`，然后用新归档运行安装脚本。安装脚本会核对两者一致。
- 站点目标是约 10 人同时使用时稳定、费用有上限、失败时关闭。可用性没有保证，也不宣称抗 DDoS。
- 共享 NAT：限流、在途上限和会话上限都按来源地址计算，同一出口地址下的人共用一份。这份额度是：同时持有 16 个会话，新会话 30 次/10 分钟，在途请求 12 个，接口请求每秒补 2 个（突发 120），手机轮询每秒补 12 个（突发 120，够约 10 部手机各每秒一次）。页面和静态文件每秒补 60 个（突发 1200）：打开一次页面约 50 个请求，同一地址 10 个浏览器同时打开约 500 个，在突发之内。
- 单来源的在途上限是 12，工作线程只有 4 个：一个地址可以占满全部工作线程，这时别的地址要排队，不会被拒绝。主队列共 20 个位置，一个地址最多占 12 个。
- 持续操作会排队：进程只用一个核。目标机实测，同一地址 10 个浏览器同时打开、登录并各做一次业务操作，全部完成，最慢的约 7 秒。接着各每 5 秒发一条、持续 150 秒，215 次全部成功，没有拒绝，但单次越来越慢：第 5 轮 0.6 秒，第 10 轮 2.9 秒，第 20 轮单次约 10 秒，最大 11.2 秒。变慢但不拒绝，离 Caddy 的 90 秒上限还很远。站点不设单会话消息上限。接口请求每秒补 2 个，这正好够 10 个人平均每人约 5 秒一次操作长期维持，更快的话只能靠 120 次突发，用完得 503。
- 慢请求体：请求体迟迟发不完时，到上游的连接约 30 秒释放，网页进程和执行器不受影响。但客户端这条连接实测既收不到响应，也不被断开（发一半后停发或持续慢发都一样，观察到 4 分钟以上）。占住的只是 Caddy 这一侧的连接，站点不宣称抗连接耗尽。
- 溢出桶：一张限流表最多记 4096 个地址，还没回满的桶不会被淘汰。表满时，新地址共用一个溢出桶，别的新地址可能先把它用完，这时新来源得 503，已在表内的地址不受影响。
- 配对令牌是持有者凭证：`/phone/<配对>` 链接里的令牌没有别的校验，持有它的人就能读这个会话的模拟短信和验证码，直到会话被重置或回收。不要转发手机页链接，也不要把它放进截图。
- 按创建来源占位：一个会话算在创建它的地址名下，换网络后不迁移，重置也不换。原地址要等这个会话被回收或驱逐之后才拿回名额。
- 费用上限是按单次调用上限预留推算的累计上限（`LIVE_BUDGET_CNY=100`，每会话 20 次调用），不等于提供商账单硬上限。预算耗尽后，在下一个交易边界退回脚本规划。
- 验证子在协议上等价于口令：读到环境文件的人不需要口令就能解锁。它防的是口令明文泄露和跨站复用，所以环境文件必须保持 0600、属主 root。
- 真模型的外发范围按带金丝雀的假端点实测，也是站内横幅的依据。脚本规划不外发。开启后每次调用是下面四步之一：
  - 意图步：消息文字和上一轮的意图标签。
  - 转账的提取步：消息文字，加上整张合成通讯录的联系人代号、姓名与号码的代号、别名（如“妈妈”“房东”），不论消息提到谁。
  - 转账的规划步：账户、联系人、金额的类型化句柄，不含消息文字。
  - 本地规则读不懂时的建议步：消息文字、其中提到的联系人代号和称呼、上一轮的意图标签。

  消息文字里只有 11 位以上的号码、邮箱、验证码和密钥换成代号，人名、地址、金额和其他文字原样发送。含密码的消息在本地拒绝，不外发。journal 保留请求摘要和模型输出，不保留消息文字。
- journal 不设自动清理，评审结束后由用户决定是否删除 `/var/lib/corridor/journal`。
- 进程日志由 journald 轮转：总量 300M，保留 14 天。Caddy 不写访问日志，错误日志和反向代理日志也被丢弃。排查上游问题时看 `journalctl -u corridor-web`。
